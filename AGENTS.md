# AGENTS.md

Guidance for anyone, human or AI agent, changing Postscrub.

## What this is

Postscrub is a Chrome MV3 extension (plain JavaScript, no build step) that bulk-cleans an X account: delete posts and replies, remove likes and reposts, unfollow, follow back. It is review-first and local-only: no backend, no analytics, no remote code.

Everything user-facing is in English.

## Layout

```
src/
  manifest.json          MV3 manifest (minimum Chrome 116)
  background.js          service worker: side panel wiring, timed sleeps for workers,
                         autoDiscardable while a job runs, X bundle parsing (xbc:bundleOps)
  inject/capture.js      MAIN-world content script at document_start: records the GraphQL
                         operations, features and bearer X's page uses, plus feature-switch
                         values from window.__INITIAL_STATE__ (deleted by X after boot)
  worker/xapi.js         API client injected into the X tab before a worker runs
  popup/                 popup UI + Quick Clean worker (runWorker)
  sidepanel/             Preview & Select UI + scanner (startPreviewScanner) and
                         selected-items worker (runSelectedDelete)
  history/               job history page (options page)
scripts/                 model-free tooling (inventory of X operations, spec checker,
                         read-only session diagnostic, syntax check)
test/e2e/                Playwright tests against a simulated x.com
```

## How workers run

Workers are functions passed to `chrome.scripting.executeScript({ func })`. Chrome serializes the function source, so **a worker cannot use anything from its file's scope**: every helper it needs is defined inside it. That is why some helpers exist in more than one worker. `worker/xapi.js` is injected first with `executeScript({ files })` and exposes `globalThis.__xbcApi` in the same isolated world.

- Page timers are throttled in background tabs; workers sleep through the service worker (`xbc:sleep`).
- A hidden tab is not rendered, so X draws no posts there. Click-mode workers must not treat an empty hidden cycle as the end of a list, nor scroll blind.
- Job state lives on `window.__xCleaner` (jobs) and `window.__xbcPreview` (scans); the popup and side panel poll it.

## X web API

The source of truth is X's own web bundle (`main.js`), not memory. Use `scripts/extract-x-operations.mjs <main.js>` to list every operation with its position, and `scripts/check-spec-against-inventory.mjs` to check any document against it.

- GraphQL: `https://x.com/i/api/graphql/<queryId>/<Operation>`. Queries are GET with `variables`, `features` (every name in the operation's `featureSwitches`, valued from the page's feature config) and `fieldToggles` only where X sends them. Mutations are POST `{"variables":{…},"queryId":"…"}`.
- Headers: `authorization: Bearer <public web token>`, `x-csrf-token` = `ct0` cookie, `x-twitter-auth-type: OAuth2Session`, `x-twitter-active-user`, `x-twitter-client-language`.
- Operations used: `UserTweets`, `UserTweetsAndReplies`, `Likes`, `Following`, `Followers`, `BlueVerifiedFollowers` (lists); `DeleteTweet {tweet_id}`, `DeleteRetweet {source_tweet_id: <original post id>}`, `UnfavoriteTweet {tweet_id}`; follow and unfollow are REST `POST /i/api/1.1/friendships/{create,destroy}.json` with a form body (`user_id` plus X's `include_*` flags).
- Query ids and features change with every X build. Discovery order in `xapi.js`: what the page requested → the loaded `main.js` → last values that worked → the build this was written against.
- Responses: `data.user.result.timeline.timeline.instructions`; tweets at `itemContent.tweet_results.result` (unwrap `TweetWithVisibilityResults`); users keep `screen_name`/`name` under `core`, `following` under `relationship_perspectives`, `follow_request_sent` at the top level.
- **Session binding**: when X enables it, `FavoriteTweet`, `UnfavoriteTweet`, `CreateRetweet` and `DeleteRetweet` must carry signatures from a key that exists only in the tab's memory. Never forge or extract it. A refused call falls back to clicking.
- **x-client-transaction-id** is generated by X's obfuscated code; Postscrub does not send it. If X starts requiring it, calls are refused and jobs fall back to clicking.

### Errors and limits (from X's error enum and handlers)

| Signal | Action |
|---|---|
| 429, 88, 143 | wait until `x-rate-limit-reset` + 10 s (15 min without it), then slow down |
| 353 | re-read `ct0`, retry once |
| 326, 445, 64, 141, 159, 89, 220, 344, 161 | stop and tell the user |
| 225, 226, 227, 228, 263, 283, 292, 315, 382 (automation) | stop and tell the user |
| 144, 34, 50, 63, 108 | already gone, skip |
| 130, 131, 5xx, network | retry with backoff |
| 401/403/404/400, session binding | refused: fall back to clicking if nothing succeeded yet |

X publishes no limit for deleting, unliking or unreposting; pacing stays near click speed (`PACE_MS` in `xapi.js`, scaled by the `apiPace` setting). Follows are limited to about 400 a day.

## Development workflow

```bash
npm run check      # node --check on every .js/.mjs file
npm run test:e2e   # all end-to-end scenarios; pass a name fragment to run a subset
```

- Every behavior change gets an end-to-end scenario in `test/e2e/run.mjs` (the simulated x.com is `test/e2e/fake-x.mjs`; it can rate limit, refuse, require session binding or flag automation).
- Validate on real X before release with `scripts/diagnose-x-session.js` (read-only, run in the x.com console) and a small test account.
- Keep permissions minimal; any new permission or host must be justified in PRIVACY.md.
- Commit messages describe the change and its reason; no tool, agent or model names, no `Co-authored-by`.
